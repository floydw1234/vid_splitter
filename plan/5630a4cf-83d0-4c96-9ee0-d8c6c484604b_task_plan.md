## Test Strategy

Use TDD for each change:
1. Write or update a failing test that describes the desired behavior.
2. Implement the minimum change to pass.
3. Refactor only after the tests are green.

Test layers:
- Python unit tests for BVF parsing edge cases.
- Python CLI/integration-style tests for `bvf_probe.py` behavior on malformed inputs.
- C# unit tests for BVF reader validation and plugin cache invalidation.
- Documentation/source-text tests for CI commands and smoke-test instructions.

Integration test data:
- Use generated `.bvf` fixtures only.
- Reuse the existing pattern in `tests/test_bvf_probe.py` that writes a valid fixture and rewrites header/manifest bytes.
- If current fixture helpers are insufficient, add a small shared helper that can generate:
  - truncated header
  - invalid index length
  - manifest offset/length outside file bounds
  - truncated asset block header
  - invalid asset block magic
- Do not depend on production media assets for corruption coverage.
- For real-media smoke checks, keep tests optional and gated exactly as the repo already does with env vars and local tool detection.

Docker / service note:
- This repo currently has no `docker-compose.yml` / `compose.yaml` and no web service under test.
- Therefore no Docker Compose startup/teardown, no localhost port assignment, and no UI/E2E browser automation are planned for this ticket.
- If a later implementation step uncovers hidden service-based tests, revisit this assumption before coding.

### 5. Jellyfin plugin cache invalidation in `csharp_plugin/SegmentServer.cs`

Desired outcomes:
- Cached manifests should invalidate when a `.bvf` file changes on disk.
- Cache should remain simple and deterministic; no hidden stale-manifest behavior after in-place rewrites.
- Logging should make cache behavior observable.

Red: add failing tests first

Add a new test file, likely `csharp_plugin.Tests/SegmentServerCacheTests.cs`:
- Test that a manifest is cached on first read.
- Rewrite the `.bvf` file in place with changed manifest content.
- Verify a subsequent read does not return stale data.
- Verify `ClearCache()` still works explicitly.

Fixture approach:
- Reuse the test style from `BVFReaderManifestTests.cs` to create small temp `.bvf` files with compressed manifests.
- If direct construction of `SegmentServer` dependencies is awkward, introduce minimal test doubles/stubs only as needed.

Implementation plan:
- Replace the current `Dictionary<string, BranchManifest>` cache with a cache record/value that also stores file freshness metadata, e.g.:
  - `LastWriteTimeUtc`
  - `Length`
- On every `GetBvfManifest()` call:
  - stat the file
  - compare to cached metadata
  - reuse only if unchanged
  - reload and replace cache entry when changed
- Prefer metadata-based invalidation on access over `FileSystemWatcher`; that is simpler and more robust for plugin runtime behavior.
- Keep `ClearCache()` and add/update logs for:
  - cache hit
  - cache miss
  - cache invalidated due to file change

Green:
- Run the new cache tests, then full C# tests.

Refactor:
- Extract a small private cache-entry type if needed.
- Avoid broad changes to unrelated plugin behavior.

Dependency:
- Should follow C# BVF reader hardening so reload paths are safe on corrupt rewrites.

## Risks / Watchpoints

- Existing tests may assert exact exception text; parser hardening should improve messages without causing unnecessary churn.
- Cache invalidation tests that rely on filesystem timestamp precision may be flaky on some filesystems. Prefer validating both `LastWriteTimeUtc` and `Length`, and rewrite content so at least one metadata field changes deterministically.
- Avoid broad logging rewrites in unrelated Python modules; keep the ticket focused on touched code paths.
- Keep corruption fixtures tiny and synthetic so the test suite stays fast.
