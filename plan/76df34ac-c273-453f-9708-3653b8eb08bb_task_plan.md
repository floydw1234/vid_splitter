# Ticket 76df34ac-c273-453f-9708-3653b8eb08bb Task Plan

## Goal
Add a reproducible Jellyfin plugin build/package/install/update workflow for `csharp_plugin/` so deployment is no longer a manual DLL copy process. The workflow must package the plugin DLL, `.deps.json`, and `ZstdSharp` dependency; keep build and manifest metadata aligned; document install/update/uninstall; and optionally provide a local `vivo` deploy helper.

## Constraints And Observations
- The current repo already has partial plugin metadata in [`csharp_plugin/build.yaml`](/tmp/terarchitect_worker_0qjvaup3/repo/csharp_plugin/build.yaml:1), version metadata in [`csharp_plugin/Directory.Build.props`](/tmp/terarchitect_worker_0qjvaup3/repo/csharp_plugin/Directory.Build.props:1), and manual install docs in [`csharp_plugin/README.md`](/tmp/terarchitect_worker_0qjvaup3/repo/csharp_plugin/README.md:46).
- There is no existing packaging script, no repository `manifest.json`, no CI/release workflow, and no `docker-compose` file in the repo.
- Because this ticket is about packaging and docs rather than UI behavior, no browser/E2E test work is currently indicated.
- Integration tests should use generated fixture files under temp directories rather than relying on a real Jellyfin server or fixed ports.
- If any helper script needs to talk to a local Jellyfin instance for optional deployment, it should accept a configurable plugin directory and should not hard-code ports or service addresses.

## Test Strategy

### Unit Tests
- Add source-text and metadata-consistency tests that validate:
  - `build.yaml` declares the expected artifacts.
  - `Directory.Build.props` version matches `build.yaml` version.
  - generated or checked-in repository `manifest.json` has the expected plugin shape.
  - README documents install, update, and uninstall flows and no longer claims manual DLL copying is the primary path.
- Add script-level unit tests that execute the packaging command against a temp fixture output directory containing fake:
  - `Jellyfin.Plugin.SmartBranching.dll`
  - `Jellyfin.Plugin.SmartBranching.deps.json`
  - `ZstdSharp.dll`
  and verify zip contents, manifest metadata, and failure behavior when an artifact is missing.

### Integration Tests
- Add a repo-native integration test that creates a temporary fake plugin build output tree, runs the packaging script end to end, and verifies:
  - output zip name and version are deterministic
  - zip contains the exact artifact set from `build.yaml`
  - generated `manifest.json` points at the expected release filename and contains checksum/timestamp/version fields
  - install-layout output can be extracted into a temp Jellyfin plugin directory without extra files
- If the packaging workflow includes an install or deploy command, add an integration test that targets a temp plugin directory on disk instead of a real Jellyfin install.
- Do not plan Docker-based integration tests for this ticket because the repo has no compose setup and the important scenarios are file-packaging behaviors, not service orchestration.
